Общие правила разработки

Всегда отвечать на русском языке.

Никогда не сливать API ключи или CLIENT SECRET в гит репозиторий, а также не использовать их в коде напрямую. Используйте файл .env для хранения конфиденциальных данных.

Комментарии и изменения. Писать комментарии только на английском языке и лишь когда это действительно необходимо (для пояснения сложной логики). Вносить в код минимально необходимые изменения — решение должно быть полным, но с минимальным «диффом»

Типизация и линтеры. Использовать строгую типизацию: включить strict в tsconfig.json, избегать any и использовать явные типы. Настроить строгий ESLint (и форматирование Prettier) для всего проекта

Лучшие практики. Следовать стандартам кодирования и best practices: не дублировать код (DRY), писать простые решения (KISS), не реализовывать функциональность заранее (YAGNI). По возможности применять TDD – сначала писать тест (или план), затем код
. Всегда проверять, что код проходит все тесты и линтер.

Компонентная структура. Разбивать интерфейс и логику на мелкие компоненты с одной ответственностью. Использовать Vue 3 Composition API (<script setup>) и декларативный стиль (избегать Options API)
. Выносить повторяющуюся логику в composables: использовать @vueuse/core для утилитарных функций, а глобальное состояние — в Pinia (через @pinia/nuxt)

Структура Nuxt 3. Придерживаться стандартной структуры проекта: pages/ (файловые роуты), components/ (переиспользуемые Vue-компоненты), composables/ (общие хуки/логика), server/ (Nitro API-функции). Воспользоваться автоматическим импортом компонентов и композаблов от Nuxt
. Для данных использовать useFetch/useAsyncData (SSR-запросы) — это обеспечивает встроенный кэш и реактивность

Серверные настройки. Поскольку бэкенда нет, всю серверную логику и чувствительные ключи обрабатывать через Nitro (файлы в server/api/). Хранить конфиденциальные параметры в runtime-config и получать через useRuntimeConfig()

TypeScript. Использовать TypeScript для всего кода. Предпочитать интерфейсы и типы, избегать any. По возможности выводить типы из схем/интерфейсов (например, через GraphQL Codegen или Zod)

ГрафQL и данные. Для запросов к API (Shikimori, Kodik и др.) использовать типизированные GraphQL-запросы через graphql-request или urql. Хранить запросы в отдельных файлах и обрабатывать ошибки. Если подключены модули (nuxt-graphql-request, urql-vue), следовать их рекомендациям. По возможности кэшировать результаты запросов (например, с помощью nuxt-cache/SWR) для производительности.

Кэширование и оптимизация. Использовать SWR-стратегию или встроенный кэш Nuxt для повторных запросов. Для изображений применять оптимизацию: формат WebP, указание размеров, ленивую загрузку (через @nuxt/image и CDN)

Методология БЭМ. Именовать CSS-классы по принципу «Блок__Элемент--Модификатор» или близкой вариации. Блок — это корневой контейнер (напр. .block), элементы внутри него получают имена вида block__element или block-element
. Всегда использовать только классы для стилизации (никаких селекторов тегов/ID) и стараться назначать не более одного БЭМ-класса на элемент

Вложенность SCSS. В SCSS-стилях объявлять блок, затем вложенными селекторами описывать его элементы через &. Например:

.block {
  /* стили блока */
  &__element { 
    /* стили элемента внутри блока */
  }

  &__element2 {
    /* стили элемента внутри блока */
  }
}
Такой подход явно связывает элемент с блоком

. Избегать глубокой вложенности: каждый уровень вложенности увеличивает специфичность селекторов и усложняет поддержку
. Не стоит вкладывать один элемент в другой (.block__elem1 { &-elem2 {…} }), лучше объявлять их рядом в одном блоке

Организация файлов стилей. По возможности держать по одному блоку на файл SCSS: тогда стили становятся проще искать и переиспользовать.
. Наименование файлов делать понятным (например, BlockName.module.scss или аналогично)

Документация. Важно документировать архитектурные решения и сложные части проекта. Хранить описания фич/модулей в Markdown (например, docs/ или plan.md).

Комментарии в коде. Комментировать код следует только при необходимости – если какая-то логика не очевидна из кода. Поясняющие комментарии писать на английском и по делу.
Избегать избыточных комментариев, стараясь делать код самодокументируемым (понятные имена функций/переменных).

Style and lint warnings. Любые предупреждения линтера или ошибок компиляции должны быть устранены.

Lazy-loading и оптимизация. Использовать ленивую загрузку компонентов и маршрутов (Vue Suspense, динамический импорт) для повышения производительности

Стилизация UI. Использовать текущие компоненты библиотеки Nuxt UI/Vue UI (как указано в настройках проекта), а не изобретать стили с нуля. Придерживаться общей темы и дизайн-системы (если есть), чтобы интерфейс был единообразным.
